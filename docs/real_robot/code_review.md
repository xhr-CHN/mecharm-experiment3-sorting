## 结论

软件状态机已经覆盖“六格识别→前排优先→底盘对准→抓取→杯左瓶右→回原点→重新识别”的目标流程。模型能够在本机实际加载，类别为 `0: cup`、`1: mouse`、`2: bottle`；但 RoboMaster 实拍已证明该权重会误分类当前金属马克杯，现由固定场景外形安全校验暂时纠正。语法、JSON 和 39 项逻辑测试通过。

杯子/瓶子抓取与两个分类盘的 12 个机械臂点均已填写；杯子抓取点已按现场反馈相对最初值累计下调45 mm，杯子放置点另下调5 mm，瓶子抓取和放置点不变。两道执行标志已按操作者明确要求改为 `calibrated=true` 和 `arm_point_profile.verified_on_this_robot=true`，因此完整真机流程不再被配置锁拦截。该人工解锁只代表执行授权，并不构成新杯子点已经通过物理验证的证据；首次运行仍可能撞地、撞杯或夹空，必须从单物体、可急停条件开始。

名义点如下：杯子抓取为 `[0,-60] → [205,-60] → [180,100]`，瓶子抓取为 `[0,-15] → [205,-15] → [180,100]`；前两段分别实现“从回中点垂直下降”和“保持抓取高度水平伸出”。杯子分类盘放置为 `[180,100] → [205,-15] → [150,110]`，瓶子分类盘放置为 `[180,100] → [205,-10] → [150,110]`，单位毫米。配置声明 `shared_by_classes=false`，允许杯瓶分别标定。

## 从同项目另一任务提取并重新核实的结论

另一任务曾在 RoboMaster SDK 0.1.1.68 上实际遇到两层连接问题：

1. SDK 内部对 `ap/sta/rndis` 使用对象身份比较，直接传入 JSON 新建的等值字符串可能导致 `proxy_addr` 未赋值；
2. 电脑不在机器人 AP 网段时，SDK 超时后可能继续产生清理异常，掩盖真正的网络错误。

本轮已在当前正式程序中重新核对并修复：JSON 值先映射为 SDK 自身常量；AP 模式先检查本机是否为 `192.168.2.x`；新增 `--connection-test`，只连接后断开，不发送任何运动命令；初始化失败会转换为清晰的 `MotionError`，同时避免旧 SDK 的清理异常覆盖原始原因。

本轮还确认当前 RoboMaster Conda 环境是 Python 3.8.20。原代码的分类盘路线测试使用了 Python 3.9 才提供的 `str.removesuffix()`；虽然主分类路径不执行该行，但 `--test-route cup-bin/bottle-bin` 会失败。现已改为 Python 3.8 兼容的字符串切片，并在 Python 3.8 环境中重新测试。

## 完整运行链路

1. 读取并校验配置。检查六格编号、ROI 不重叠、模型类别、路线单步上限、转角上限和机械臂点。
2. 所有模式都会检查 12 个机械臂点的结构、数值范围及共享一致性；`--execute` 还要求 `calibrated=true` 和 `arm_point_profile.verified_on_this_robot=true`。
3. 加载 `best.pt`，实际模型类别必须与配置严格一致，否则立即停止。
4. 连接 RoboMaster；AP 模式先确认本机网络地址，再把连接类型映射为 SDK 常量。
5. 启动相机和夹爪状态订阅，等待 5 秒安全倒计时。
6. 摄像头安装在机械臂上，因此执行模式在第一次扫描和每次抓取后复核扫描前都显式执行机械臂回中，等待默认 `0.8 s`，再丢弃 3 帧并读取 12 帧。ROI 标定使用 `--preview-recenter` 获得同一回中视角；该模式只回中和扫描，不执行底盘、夹爪或分类动作。检测框中心只属于一个 ROI 时才计入对应格子，随后按帧投票。
7. 格子状态分为：目标候选、空、鼠标/不支持、命中不足、类别冲突。
8. 按 `G1→G2→G3→G4→G5→G6` 选择目标。更高置信度的后排物体不会越过前排优先级。
9. `G4/G5/G6` 分别受 `G1/G2/G3` 通道联锁；前方同列不为空时不进入后排。
10. 机械臂先回中；底盘横移到目标列，再前进到名义抓取距离。
11. 夹爪张开，机械臂依次到预抓取点、抓取点，闭合夹爪。
12. 闭合后丢弃运动过程中的旧状态，等待新的 DDS 状态。默认只把 `normal`（夹爪停在中间位置）作为“可能夹住杯/瓶”的证据。
13. 抬升并回中，底盘按去程的逆序反向路线回到原始拍摄位。
14. 杯子执行左转 90°、前进、放入左盘、后退、右转 90°；瓶子执行对称的右侧路线。
15. 再次回到原始拍摄位扫描。只有源格被识别为空，才计为一次完成。
16. 达到目标数量，或连续两轮没有安全候选时结束，并写入日志和摘要。

## 可能无法完成指定任务的原因

### 运行前直接阻塞

- 任一机械臂点缺失、格式错误、超过程序数值保护范围，或共享配置中的杯/瓶点不一致：配置校验直接失败。
- `calibrated=false` 或 `arm_point_profile.verified_on_this_robot=false` 时程序会主动拒绝 `--execute`；当前随附配置的两个标志均为 `true`，因此不会触发这项拒绝。
- Jetson 缺少与 JetPack 匹配的 PyTorch、Ultralytics、OpenCV 或 RoboMaster SDK。
- 配置使用 `device="0"`，但系统没有可用 CUDA GPU，YOLO 首次推理会失败。CPU 环境应改为 `device="cpu"`。
- AP 模式下未连接 RoboMaster 热点，本机不在 `192.168.2.x` 网段。
- 机器人未开机、不是正确连接模式、已被其他控制器占用，或视频流启动失败。
- 模型文件缺失、损坏，或模型内的类别名称不再是 cup/mouse/bottle。
- 日志目录不可写，程序无法保存必要的扫描证据图。

### 识别不到或识别错误

- 六个 `roi_norm` 只是初始建议；相机高度、俯角或安装位置改变后，检测框中心可能落在 ROI 外。
- 摄像头随机械臂移动。正式模式虽然每次扫描前都会回中，但回中重复误差、支架松动、线缆拉扯或振动可能让 ROI 整体偏移；预览模式不会自动回中，必须人工建立相同姿态。
- 近排遮挡远排，尤其是高瓶子；后排物体在画面中太小也会降低置信度。
- 杯把、反光瓶、透明瓶、弱光、逆光、复杂地面纹理或训练域差异会造成漏检/误检。
- 12 帧中少于 5 帧命中会标为 `uncertain`；杯/瓶投票占比不足 0.7 会标为 `ambiguous`，程序不会抓取。
- 模型之外的未知物体可能完全没有检测框，因此会被当成空格；鼠标因为属于模型类别，能够明确标成 `unsupported`。
- 一个格子放入两个物体时，程序只取每帧置信度最高的检测，不保证夹取对象与类别稳定一致。

### 底盘没有对准或没有回到原点

- 所有路线都是开环位移。麦克纳姆轮打滑、电量、负载、地面缝隙和轮胎磨损都会造成误差。
- `0.18 m` 是名义抓取距离，不是实测的“底盘中心到物体”安全距离；机械臂基座并不一定等于底盘几何中心。
- 两排边缘只间隔 7 cm。进入后排前必须确认同列前排确实清空，并确认底盘宽度不会扫到相邻列物体。
- 理论上的逆路线净位移为零，不代表真实回零。回零误差会进一步造成下一次 ROI 错位。
- 分类盘实际中心与配置不一致，或盘太小，可能导致物体落到盘外。
- 程序没有动态避障；线缆、人员、掉落物或未清除的鼠标都会造成碰撞风险。

### 机械臂或夹爪抓取失败

- `moveto(x,y)` 坐标依赖本次上电零点；重新装配、上电初始姿态变化后，旧坐标可能失效。
- 本版按要求让杯和瓶共用同一组名义点，但这只适用于瓶身下部存在与杯身相近、稳定且不易滑动的夹持段；若瓶身较细、重心高、表面光滑或可变形，可能夹空、打滑或倾倒，必须改成独立瓶子标定点。
- 杯把朝向错误可能让夹爪撞到把手；透明瓶或轻瓶可能在接触时被推倒。
- 夹爪功率或闭合时间不足会滑落，过大则可能挤压物体或使机器人姿态变化。
- `normal` 仅表示夹爪没有完全张开/闭合，不是力传感器；摩擦卡住也可能产生假成功，细小物体也可能完全闭合而被判失败。
- 机械臂回中路径本身也必须验证；夹住高瓶时回中可能与相机架、车体或物体碰撞。

### 状态机主动停止

- 某格抓取失败一次后达到默认失败上限，该格本轮不再尝试。
- 前排格子是鼠标、识别不确定或抓取失败时，同列后排会保持阻塞。这是防碰撞策略，但会导致后排杯/瓶没有被处理。
- 任一底盘/机械臂 Action 被拒绝、失败或超过 15 秒，程序停止后续流程；在姿态未知时不自动继续。
- 相机读取、YOLO 推理、绘图或保存扫描图发生异常，会终止任务。正式自动分类依赖视觉，所以这里采用失败即停，而不是盲目继续动作。
- 分类后只验证“原格为空”，不能证明物体确实进入正确分类盘；掉在路上同样可能被计为源格清空。

## 推荐真机门槛

按以下顺序逐级通过，不要直接跑六件：

```bash
python3 desktop_sorter.py --validate-config
python3 desktop_sorter.py --connection-test
python3 desktop_sorter.py --preview-recenter --no-display
python3 desktop_sorter.py --execute --test-route G1
python3 desktop_sorter.py --execute --test-route G4
python3 desktop_sorter.py --execute --test-route cup-bin
python3 desktop_sorter.py --execute --test-route bottle-bin
```

然后用空载、空杯、空瓶逐点核对已填写的名义坐标。确认这 12 个点后设置 `arm_point_profile.verified_on_this_robot=true`；完成 ROI、底盘和整套流程标定后再设置 `calibrated=true`。分别完成一次单杯和单瓶测试，再测试一排，最后才运行：

```bash
python3 desktop_sorter.py --execute --max-objects 6 --no-display
```

验收视频应同时覆盖六格、机器人和左右分类盘。日志用于定位程序状态，不应单独当作“正确进入分类盘”的证据。
